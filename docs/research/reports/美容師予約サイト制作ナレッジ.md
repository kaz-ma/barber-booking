# 排他制約と空き枠のみ表示で一人バーバーの即時予約を完結させる

Neuer Barber（大阪・長田健豊、1人1席、18:00–24:00・30分刻み・全メニュー60分仮・月曜定休仮）の日英予約サイトは、**Next.js 16.4 App Router + next-intl 4 + Neon Postgres（Vercel Marketplace、Free）+ Drizzle** を骨格にし、ホスティングは **Vercel Pro（$20/月、hnd1 東京リージョン）を第一候補**とする（Vercel Hobby は Fair Use Guidelines で「non-commercial personal use only」と定められ、営業中の美容室の予約サイトは商用に該当するため本番には使えない。代替は Cloudflare Workers Paid $5/月＋`@opennextjs/cloudflare`、Workers Free は SSR の CPU 10 ms 上限で不採用、Cloud Run は運用負荷が高い次点）。二重予約を **PostgreSQL の `EXCLUDE USING gist` 排他制約**で最終防衛し、顧客 UI を「同一ページ内の段階開示フォーム → 週ストリップ＋1日最大 11 個の開始時刻ボタン（空き枠のみ）→ Check-answers 型確認 → スクリーンショット前提の完了画面＋トークン付きキャンセルリンク」に絞るのが、8 領域の調査を突き合わせた結論である。ただし本案件については、開発者の最終判断として、友人のための無償制作であることから **Phase 1 本番を Vercel Hobby で運用**し、Fair Use Guidelines 上の規約リスク（警告・停止）は開発者・クライアントが了承済みである。Vercel から警告・停止があれば Vercel Pro または Cloudflare Workers Paid へ移行し、紹介案件など有償案件では本レポートの推奨どおり最初から Pro を使う。自作が正当化される根拠は市場側にあり、RESERVA・STORES 予約の無料枠は**月 50 件**で一人店の想定件数（月 150–200 件）を確実に超え、Hot Pepper Beauty は掲載料非公開＋予約手数料 2% の固定費構造で、大阪の英語対応バーバーの公開情報は電話番号のみという空白がある。デザインはブランド色 **#7c0000 がベージュ #f4ecdd 上で 9.63:1（AAA）**を満たす一方、チャコール #191919 上では **1.55:1** で使えないため、ベージュ×えんじのライトテーマを核に 3 層トークンで組む。管理 PWA のプッシュ通知は iOS では「Safari の共有メニューからホーム画面に追加したウェブアプリ」内でしか動かず、購読が静かに失効するため、Web Push を best-effort と割り切り「起動時の購読再確認＋可視時ポーリング＋日次サマリー」で補う。制作プロセスは「第 1 回会議でヒアリング → 第 2 回会議で要件定義書ドラフト・価格表・デザイン方向案 2〜3 案を同時提示 → 1 案に収束」とし、修正回数 2 回・検収 14 日・変更要求は別見積を契約に明記する。運用は決済なし前提で「請求より予防」（前日までセルフキャンセル可、無断キャンセルは `no_show_count` で段階制限、キャンセル料は消費者契約法 9 条の範囲内の裁量条項）に寄せ、将来の顧客チャットは LINE 公式アカウントを主軸、電子カルテは要配慮情報を別テーブルに分離して同意を取る設計で接続できる。初回調査時はネットワーク制限により Vercel・個人情報保護委員会・HPB 等の一次ページ本文を取得できなかったが、2026-10-10 にネットワークを開放して 5 本の検証ノート（`09_gap_*`）で原典照合を行い、本レポートはその結果（ホスティング前提の変更、Push ペイロード形式、カレンダー記号、法務記載の訂正）を反映済みである。巻末の「検証結果」表に確認済み・訂正・未解決の項目を列挙する。

## 無料 SaaS は月 50 件で破綻し、大阪の英語オンライン予約は空白である

自作の是非は「SaaS で足りるか」で決まる。it-trend は 2026 年 4 月時点で美容室向け予約システム 16 選を公開し、選定軸として集客サイト連携・料金体系の透明性・操作性・サポートを挙げるが（[it-trend.jp](https://it-trend.jp/reservation/article/409-5092)）、一人店が実質無料で使える枠は限られる。**RESERVA Free は月 50 件予約・登録顧客 250 件まで**、有料は年払い月額ブルー 3,850 円（月 200 件）からで、LINE 連携 3,300 円/月やオンライン決済手数料 4.9% が別途かかる（[saas.imitsu.jp](https://saas.imitsu.jp/cate-reservation/service/2735/price)、[atsoho.com](https://atsoho.com/blog/compare-reserva)）。**STORES 予約も Free は月 50 件**、スモールは年契約で月額 9,790 円（税込、複数月契約 12,980 円）・月 200 件、チームは年契約 19,690 円（複数月 22,880 円）・**月 300 件**、最低利用期間 3 か月である（[stores.fun/reserve/pricing](https://stores.fun/reserve/pricing) で 2026-10-10 に確認。以前「チーム 5,000 件／77,000 円」としていたのはエンタープライズの値で誤り）。RESERVA の数値も公式料金ページ（[biz.reserva.be/price](https://biz.reserva.be/price/)）で一致を確認した。minimo は月額 0 円で**来店時のみ手数料 110〜880 円/件**（施術料金 0 円→110 円、〜2,200 円→440 円、〜6,600 円→660 円、6,601 円以上→880 円、[minimodel.jp/info](https://minimodel.jp/info)）で、客単価 4,000〜10,000 円帯では 1 件 660〜880 円＝売上の 7〜16% になる。Square 予約はフリー無料・プラス 3,000 円/店舗・プレミアム 8,000 円/店舗で、対面決済手数料 2.5%〜が乗る（[squareup.com FAQ](https://squareup.com/jp/ja/appointments/faq)、[squareup.com](https://squareup.com/jp/ja/townsquare/appointment-system-pricing)）。Hot Pepper Beauty は 2025 年 12 月時点で無料掲載不可、掲載料は「エリアやプランによって異なる」として非公開で、予約ごとに 2% の手数料がかかると解説されている（[atsoho.com](https://atsoho.com/blog/hot-pepper-listing-fees-expensive)、[freee.co.jp](https://www.freee.co.jp/personal-business/guide/articles/1907/)、[squareup.com](https://squareup.com/jp/ja/townsquare/the-publication-fee-of-hot-pepper-beauty)）。海外勢の Fresha は定額無料モデルを廃止してソロ月額 19.95 ドル＋マーケットプレイス経由の新規予約に 20% 手数料へ移行しており、日本語・国内決済対応は確認できなかった（[pabau.com](https://pabau.com/blog/fresha-vs-booksy/)）。本件の営業条件（週 6 日 × 最大 11 枠 = 週 66 枠）で稼働率が半分でも月 140 件前後になるため、無料枠は初月から超過し、最低でも月 3,850〜9,790 円の固定費が発生する。これが「なぜ SaaS でなく自作か」の定量的根拠で、計画書に転記できる。

価格設計のサニティチェックには HPB 掲載店の実勢が使える。大阪のメンズカットは初回 4,400 円・シャンプー無し 30 分 3,850 円・眉カット付き 5,800 円（[beauty.hotpepper.jp](https://beauty.hotpepper.jp/slnH000550607/coupon/)）、カット込みのツイスト／波巻きパーマは新規クーポンで 7,980〜12,800 円（[beauty.hotpepper.jp 西梅田](https://beauty.hotpepper.jp/slnH000502567/style/)、[梅田茶屋町](https://beauty.hotpepper.jp/slnH000499535/style/L213912818.html)）。美容センサス 2024 年上期の**男性 1 回あたり利用金額は 4,708 円**で、男性のカラー・パーマ利用率は前年から 2 ポイント以上増加した（[hba.beauty.hotpepper.jp](https://hba.beauty.hotpepper.jp/wp/wp-content/uploads/2024/06/census_hair_20240625.pdf)）。市場全体は 2026 年上期発表で前年比 -5.9% の 1 兆 3,063 億円と縮小しつつ理容室だけは前年を下回っておらず（[prtimes.jp](https://prtimes.jp/main/html/rd/p/000003210.000011414.html)）、「メンズ×デザインパーマ」で高単価化する一人バーバーの戦略は市場トレンドに合う。女性のネット予約率は 2025 年上期で 59.2%、20 代では 75.8% に達しており（[crex-data.com](https://www.crex-data.com/industry/education/beauty-salon/customer-acquisition)）、若年客にとってネット予約は前提条件になっている。

## ベージュ×えんじのライトテーマは AAA を満たし、3 層トークンで守る

### タイポグラフィは Lato 先行・Noto Sans JP フォールバックで、日本語本文の行間を 1.7 に上書きする

タイプスケールは Tailwind v4 の既定値（xs 12px/lh 16 … base 16/24 … 2xl 24/32 … 4xl 36/40）に揃えれば設計とコードが一致する（[Tailwind CSS docs: font-size](https://tailwindcss.com/docs/font-size)）。ただし Tailwind の base 行間 1.5 は欧文基準であり、W3C の日本語組版処理の要件（JLREQ）は「日本語組版の行間は欧文より大きくなる」「横組の 1 行は最大 40 字程度」「和欧混植では和文と欧字・数字の間を四分アキ（1/4em）」と定めている（[W3C JLREQ](https://www.w3.org/TR/jlreq/)）。推奨値は **本文 16px/行間 1.7（`--text-base--line-height: 1.7`）、最小 12px、入力欄 16px 以上**で、下限の根拠は Apple HIG の iOS 既定 17pt・最小 11pt と、細いウェイトを避けて Regular〜Bold を使う指針にある（[Apple HIG: Typography](https://developer.apple.com/design/human-interface-guidelines/typography)）。本文の最大幅は JLREQ の 40 字 × 16px ≒ 640px に合わせ `max-w-[42rem]` 程度に抑える。WCAG 2.1 SC 1.4.12 Text Spacing は「日本語への word-spacing 適用は効果がなかった」と明記し、各言語のローカルな可読性ガイダンス（JLREQ 等）に従うことを推奨しているため（[WCAG Understanding: Text Spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)）、字間はデジタル庁デザインシステムのタイポグラフィ（2026-08-05 更新）が Standard テキストの letter-spacing を「0、1%（0.01em）、2%（0.02em）」、本文行高を 160〜175%（170/175% は「心理的負荷の軽減」）、フォントサイズを「基本的に 16 CSS px 以上」と定めているため（[design.digital.go.jp](https://design.digital.go.jp/dads/foundations/typography/)）、**本文 0〜0.02em**（当初推定の 0.04em は過大）とし、`palt` は見出しのみに限定する（Google Fonts 配信の Noto Sans JP でも日本語スライスの GPOS に `palt` が保持されていることを fontTools で確認済み、[09_gap_competitors_design.md](../research_notes/美容師予約サイト制作ナレッジ/09_gap_competitors_design.md) D-9）。

フォント読み込みには重要な制約がある。Next.js 内蔵の Google Fonts データでは **Noto Sans JP の preload 可能サブセットは cyrillic/latin/latin-ext/vietnamese のみで `japanese` が存在しない**（[vercel/next.js font-data.json](https://github.com/vercel/next.js/blob/canary/packages/font/src/google/font-data.json)）。したがって `Noto_Sans_JP({ weight: 'variable', subsets: ['latin'], display: 'swap' })` として欧文だけ preload し、日本語グリフは Google Fonts の unicode-range 分割に任せる。`display` の既定は `swap`、`adjustFontFallback` は既定 true で CLS を抑える（[Next.js docs: Font Module](https://nextjs.org/docs/app/api-reference/components/font)）。Lato は Google Fonts 版が静的フォントで latin/latin-ext のみ（[google/fonts: lato METADATA.pb](https://github.com/google/fonts/blob/main/ofl/lato/METADATA.pb)）なので `weight: ['400','700']` に絞る。`font-family` は `var(--font-lato), var(--font-noto-sans-jp), system-ui, sans-serif` の順で、料金・時刻の数字を Lato に、和文を Noto Sans JP に自動で振り分ける。完全自前配信に進む場合は FontTools で JIS 第 1・2 水準に絞り `--layout-features='*'` で palt/kern を保持して WOFF2 化すると 50% 以上削減できた事例がある（[uhiyama-lab.com](https://uhiyama-lab.com/ja/blog/webdev/optimize-subset-fonttools/)）。

### カラーは #7c0000 を CTA・空き・選択中の 3 用途に限定し、ダーク面では明るいトーンに差し替える

WCAG 2.x の相対輝度式で算出した実測値は、**#7c0000 on #ffffff = 11.31:1、on #f4ecdd = 9.63、on #e9dcc3 = 8.34、on #d9c6a0 = 6.75** で、ベージュ系の上では通常文字の AAA（7:1）または AA（4.5:1）を満たす。**#191919 on #f4ecdd = 14.98** で本文は余裕があり、**バーガンディ地にベージュ文字の CTA は 9.63:1** で AAA になる。一方 **#7c0000 on #191919 は 1.55:1** で UI 部品の 3:1 にも届かない（算出式は [WCAG Understanding: Contrast (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)）。閾値は SC 1.4.3 が通常文字 4.5:1・大きな文字（18pt≒24px、太字 14pt≒18.5px）3:1、SC 1.4.11 が UI 部品と状態表示 3:1、SC 1.4.1 が「色だけで情報を伝えない」で、disabled 部品は 1.4.11 の対象外である（[Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)、[Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)）。Material 3 はライトで primary40・ダークで primary80 というトーン入れ替えを定義しており（[Material Components: Color theming](https://github.com/material-components/material-components-android/blob/master/docs/theming/Color.md)）、これに倣って #7c0000 を tone40 とする 10 段パレット（95 #fbe9e9 / 80 #e8a3a3 / 70 #d9777b / 40 #7c0000 / 20 #450000 …）を作り、ダーク面のアクセントは **#d9777b（5.76:1）〜#e38b8b（6.98:1）**に差し替える。

空き状況のセマンティックカラーは赤/緑対比を避け、Okabe–Ito の色覚安全パレット（青 #0072B2、橙 #E69F00、青緑 #009E73 等）を起点にする（[clauswilke/colorblindr](https://github.com/clauswilke/colorblindr/blob/master/R/palettes.R)）。ただしベージュ上では Okabe–Ito 青 #0072b2 が 4.42:1、青緑が 2.91:1 と不足するため、**空きあり = 濃い青 #0f5f8f＋「◎」、満席 = 中立グレー＋取り消し線＋「×」**の 2 値とし、記号・ラベルを必ず併用する。Hot Pepper Beauty の公式ガイドは「◎ 即時予約可／○ 仮予約可／× 予約できません」の 3 記号を定義し △ は存在しないため（[beauty.hotpepper.jp/doc/guide/reserve.html](https://beauty.hotpepper.jp/doc/guide/reserve.html)）、即時確定のみの本サイトで ○ や △ を使うと HPB 利用者に「仮予約」「残りわずか」と誤読される。橙は将来「残りわずか」状態を追加する場合の予備トークンに留める。Material 3 のコントラスト基準（大きな文字・図形・ボタン容器 3:1、小さな文字 4.5:1、無効状態は要件外）は公式ページで確認済みで（[m3.material.io](https://m3.material.io/foundations/designing/color-contrast)）、× セルの薄灰はこの「無効状態」として許容する。バーガンディは「選択中」の 1 用途に限定して状態色と意味を衝突させない。Apple HIG も「主にモノクロームな背景のアプリではブランド色をアクセントに」「色だけで区別しない」「ライト/ダーク両方で確認」と求めている（[Apple HIG: Color](https://developer.apple.com/design/human-interface-guidelines/color)）。**採用判断**: 顧客サイトは Phase 1 ではライトテーマのみ（ブランド体験の核）、管理 PWA は `prefers-color-scheme` 追従＋手動固定。トークンはダーク対応可能な構造で最初から定義しておく。

### スペーシング・ターゲット・モーションは Tailwind と Material の既定値をそのまま使う

Tailwind v4 の基準は `--spacing: 0.25rem`（4px）、ブレークポイントは sm 640 / md 768 / lg 1024 / xl 1280 の mobile-first である（[Tailwind CSS docs: theme](https://tailwindcss.com/docs/theme)）。4/8/12/16/24/32/48/64/96 を主要段階とし、ガター 16px（≤640）/ 20–24px（≥768）、セクション間 48–64px（モバイル）。予約フローは 320〜430px を主戦場にし、`md:` で「左: カレンダー／右: 時間枠＋サマリー」の 2 カラム化、320px 幅で横スクロールが出ないこと（WCAG 1.4.10 Reflow）を必ず確認する（[WCAG Understanding: Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)）。タッチターゲットは WCAG 2.2 SC 2.5.8 の **24×24 CSS px を絶対下限**（UA 既定コントロールと間隔例外あり）（[Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)）、Apple HIG の **44×44pt を標準**（[Apple HIG: Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)）とし、日付セル 40–44px 正方（7 列 × 44 = 308px < 320px）、時間枠チップ高さ 44–48px、主要 CTA 高さ 48–56px・全幅・下部固定を採用する。下部固定バーは `padding-bottom: max(16px, env(safe-area-inset-bottom))` でホームインジケータを避け（[CSS env()](https://drafts.csswg.org/css-env-1/#safe-area-insets)）、`scroll-padding-bottom` でフォーカス要素が隠れないようにする（SC 2.4.11、[Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)）。

モーションは Material のトークンをそのまま採用する。duration は short1–4 = 50/100/150/200ms、medium1–4 = 250–400ms、long1–4 = 450–600ms、easing は standard `cubic-bezier(0.2,0,0,1)`、emphasized-decelerate `(0.05,0.7,0.1,1)`、emphasized-accelerate `(0.3,0,0.8,0.15)` で、「移動距離が大きいほど長く」が原則である（[Material Components: Motion theming](https://github.com/material-components/material-components-android/blob/master/docs/theming/Motion.md)、m3.material.io の公式トークンページで一致を確認）。M3 の推奨ペアは **Emphasized 500ms（画面内の移動）／Emphasized decelerate 400ms（入場）／Emphasized accelerate 200ms（退場）／Standard 300ms／Standard decelerate 250ms／Standard accelerate 200ms** で、「Standard は Emphasized 非対応の iOS・Web 向けフォールバック」とされる（[M3: Applying easing and duration](https://m3.material.io/styles/motion/easing-and-duration/applying-easing-and-duration)）。なお同ページは「Expressive 更新ではスプリング物理に移行し、easing/duration 体系はメンテナンス終了」と注記しているが、スプリングの数値仕様は公開されていないため本件はトークン値を使う。予約サイトの辞書は、ボタン押下 100ms・フォーカスリング 150ms・時間枠トグル 150–200ms・ボトムシート入場 400ms（emphasized-decelerate）/退場 200ms（emphasized-accelerate）・月切替スライド 250ms・ステップ遷移 300ms（standard）。HIG は「頻繁な操作に動きを足さない」「動きを唯一の情報伝達手段にしない」と述べ（[Apple HIG: Motion](https://developer.apple.com/design/human-interface-guidelines/motion)）、`prefers-reduced-motion: reduce`（[CSS Media Queries 5](https://drafts.csswg.org/mediaqueries-5/#prefers-reduced-motion)）では移動系を止めて 100ms のフェードだけ残す。パララックスやスクロール連動は不採用（WCAG 2.3.3、[Animation from Interactions](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)）。ヴィンテージ演出はヒーローのバーバーポール回転 1 つに限定し、reduced-motion で静止画に落とす。

### トークンは「プリミティブ → セマンティック → Tailwind 接続」の 3 層にする

Tailwind v4 の `@theme` で定義した変数はユーティリティと CSS 変数の両方になり、`@theme inline` は値を展開するため `var()` 参照をそのまま使える（[Tailwind CSS docs: theme](https://tailwindcss.com/docs/theme)）。ダークは `@custom-variant dark (&:where([data-theme=dark], [data-theme=dark] *))` でクラス/属性切替にする（[Tailwind CSS docs: dark mode](https://tailwindcss.com/docs/dark-mode)）。推奨構成は、(1) `:root` にプリミティブ（`--burgundy-40: #7c0000`, `--paper-98: #f4ecdd`, `--ink-10: #191919`, `--paper-texture`）、(2) `:root` と `[data-theme=dark]` でセマンティック（`--bg`, `--fg`, `--fg-muted`, `--accent`, `--on-accent`, `--border`, `--ring`, `--status-open/few/full/closed`）、(3) `@theme inline` で `--color-bg: var(--bg)` のように接続し `--color-*: initial` で既定パレットを捨てる、という形である。トークン名は用途名（`--status-open`）で付け、色名（`--green`）を避けると色覚対応で色相を変えてもコードが変わらない。next/font の `variable: '--font-lato'` を `--font-sans` に接続する。

### 写真・ロゴ・テクスチャは「低コントラストの紙、単色ロゴ、統一トーンの写真」で揃える

事例レビューに共通するプレミアム条件は、配色 2〜3 色、大きな余白、統一トーンの写真、料金の透明表示、1 タップ以内の予約 CTA である（[sidora.ch Barbury](https://www.sidora.ch/en/projects/barbury-premium-barbershop-website)、[nanoglobals.com](https://nanoglobals.com/barbershop-websites/)、[cyberoptik.net](https://cyberoptik.net/blog/best-barber-shop-websites)）。クラフト紙テクスチャは輝度差 ±3〜5% に抑え、256–512px タイルを `mix-blend-mode: multiply` で #f4ecdd の上に重ね、文字コントラストは「テクスチャの最暗ピクセル vs 文字色」で判定する（#5c5046 のミュート文字でも 6.65:1 なので余裕がある）。入力欄とカードは無地にしてフォーム可読性と図地の区別を作る。ロゴは「フルカラー／単色バーガンディ／単色チャコール／ダーク用ベージュ」の 4 バリアントを SVG で用意し、紙テクスチャ上で埋もれる細い線（ヒゲの輪郭）は 24–32px 用の簡略版で太くする。WCAG 1.4.11 は意味を持つアイコンに隣接色 3:1 を要求し「細い線は実効コントラストが落ちる」と注意している（[Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)）。写真は暖色寄り・やや低彩度・黒を #191919 付近に締める 1 つのグレードに統一し、カード 4:5／ヒーロー 3:2 の 2 比率、`next/image` で WebP/AVIF 配信、LCP 画像は `priority` とする。

## 段階開示フォームと 11 枠の週ストリップが最少タップで確定させる

### 入力は同一ページ内 accordion 型、進捗は粗い 4 段、検証は blur 後

GOV.UK は「1 ページ 1 問」を既定の出発点とし、低確信ユーザー・モバイル・エラーと分岐の扱いに強いとする（[GOV.UK: Question pages](https://design-system.service.gov.uk/patterns/question-pages/)、[GDS: One thing per page](https://designnotes.blog.gov.uk/2015/07/03/one-thing-per-page/)）。一方 Baymard は accordion 型チェックアウトがベンチマークで従来型より **19.2% 高い**スコアだが形式自体が品質を保証せず、「1 ページ/accordion/複数ページのどれかより、何をどう聞くかの方が重要」と結論づけ、完了したステップは要約に畳み、単一 URL ではブラウザ「戻る」で全体を失う問題を指摘している（[Baymard: Accordion-Style Checkout](https://baymard.com/blog/accordion-style-checkout)、[Accordion usability](https://baymard.com/blog/accordion-checkout-usability)、[One-page checkout](https://baymard.com/blog/one-page-checkout)）。本件は項目が 5 グループ（メニュー・氏名＋ふりがな・職業・電話・備考）と少ないため、**採用案は「同一ページで前項目完了後に次を開示する accordion 型、完了項目は要約表示してタップで再編集、`history.state` で段階を管理して戻るで失わない」**である。進捗表示は GOV.UK が「リサーチで必要と分かった場合のみ」とし、NN/g は現在地と残りの明示・「Next」より次ステップ名のラベルを推奨するため（[NN/g: Wizards](https://www.nngroup.com/articles/wizards/)）、「1. メニューを選ぶ → 2. お客様情報 → 3. 日時を選ぶ → 4. 確認」の粗い 4 段ステッパーに留める。ラベルは HPB の実表示「クーポン・メニューを選ぶ → 日時を指定する → 予約手続きへ」に倣って動詞形で統一する。なお HPB・RESERVA はいずれも日時選択を情報入力より前に置く（HPB は「メニュー → 日時（指名は日時画面内） → リクルート ID ログイン → 情報入力」）ため、クライアント要望どおり「情報入力 → 日時」にするか HPB 順「メニューを選ぶ → 日時を選ぶ → お客様情報 → 確認」にするかは第 2 回打ち合わせで確認する【要確認】。

検証タイミングは各機関で一致している。NN/g は「フィールドを離れるまでエラーを出さない」「該当フィールドの横に置く」「同じエラーが 1 回の試行で 3 回以上出るなら UI の欠陥」（[NN/g: Errors in Forms](https://www.nngroup.com/articles/errors-forms-design-guidelines/)）、Baymard は早すぎる検証を避け修正されたら消す・EC の 32% がフィールド検証を提供していない（[Baymard: Inline Form Validation](https://baymard.com/blog/inline-form-validation)）、A List Apart の実験では最良のインライン検証でエラー 22% 減・完了時間 42% 減（[A List Apart](https://alistapart.com/article/inline-validation-in-web-forms/)）。反証として UX Movement は離脱直後の即時表示でエラーが増えた研究を引く（[UX Movement](https://uxmovement.medium.com/why-users-make-more-errors-with-instant-inline-validation-945aaf4c370a)）。**採用案は「blur 後に表示、修正で即消去、送信時はサマリー＋該当箇所」の三層**で、エラー文は GOV.UK 流の「電話番号を入力してください（例: 09012345678）/ Enter your phone number」とし、「必須です」「An error occurred」のような汎用文を禁止する（[GOV.UK: Error message](https://design-system.service.gov.uk/components/error-message/)）。

### カレンダーは週ストリップ＋縦リスト、◎は「この時刻から 60 分確保できる」を保証する

Hot Pepper Beauty の実フロー（2026-10-10 に大阪・阿倍野の理容室 3 店で実機確認、[09_gap_competitors_design.md](../research_notes/美容師予約サイト制作ナレッジ/09_gap_competitors_design.md) §A）は「クーポン・メニューを選ぶ → 日時を指定する（7 日×30 分の週グリッド。スタイリスト指名は同じ画面の上部チップ）→ リクルート ID ログイン → 情報入力 → 確認」で、記号の公式定義は「◎ 即時予約可／○ 仮予約可／× 予約できません」、△ は存在しない（[beauty.hotpepper.jp/doc/guide/reserve.html](https://beauty.hotpepper.jp/doc/guide/reserve.html)）。メニュー一覧には価格のみで所要時間は出ず、選択後に「施術時間合計（目安）」を表示する。直前枠は × ではなく「TEL：直前のため、お電話でお問い合わせください」に置換され、凡例直下に電話番号リンクを置く。締切が何分前かは画面・ガイドのどこにも書かれておらず（当日 19:19 時点で 19:00 枠が TEL、19:30 枠が ×）、「30 分後から選択可能」という二次情報（[and-us.jp](https://and-us.jp/5606/)）は未確認のままである。HPB では 30 分刻みの◎が施術時間分の連続空きを意味しないケースがあり注意喚起されているが（[HPB サロンブログ 2018](https://beauty.hotpepper.jp/slnH000263848/blog/bidA019690176.html)）、本件は全 60 分固定なので「◎ = その時刻から 60 分確保可能」を保証でき、これが差別化点になる。Smashing Magazine は日付 2 タップ・時間枠込み 5 タップの予算と、空き/価格をカレンダー内に併記する指針を示す（[Smashing: Date and time picker](https://www.smashingmagazine.com/2017/07/designing-perfect-date-time-picker/)）。Calendly の予約ページは月表示のみで、対面イベントではタイムゾーン固定を推奨し（[Calendly Community](https://community.calendly.com/how-do-i-40/change-booking-page-view-from-month-to-weekly-view-embed-calendly-in-lightspeed-3564)、[Calendly Help](https://calendly.com/help/time-zones-overview)）、Cal.com は月/週/カラムの 3 レイアウトと最短通知内の枠非表示を持つ（[Cal.com Docs: Booker](https://cal.com/docs/atoms/booker)、[Minimum notice](https://cal.com/docs/core-features/event-types/minimum-notice)）。

本件は 18:00〜24:00 で 60 分メニューなら **開始時刻は 18:00〜23:00 の最大 11 枠**しかない。**採用案は「横スクロールの週ストリップ（初期位置は今日、過去日と月曜は非活性）＋選択日の開始時刻ボタン縦リスト（空き枠のみ、`18:00–19:00` の開始–終了表記）」**で、日 1 タップ＋時間 1 タップに収まる。月グリッドは「空きのある日を探す」二次ビューとして用意し、全枠×の日は日付自体をグレーアウト＋「満席」ラベルにする。凡例（◎＝予約できます（この時刻から施術開始）/ ×＝予約できません）は HPB と同じく**グリッド直下**に 2 行で置き、○・△ は使わない。◎は画像でなくテキストにし色は 3:1 以上、× は低コントラストの灰（HPB: #999 on #EEE）で「押せない」ことを伝える。HPB は締切後の枠を「TEL」に置換して電話番号を凡例直下に出すので、本サイトも「本日の残り枠は電話で」の連絡導線を同じ位置に出す。締切時間は HPB では非表示だが RESERVA は「予約締切：6時間前まで」と文で明記しているため（[reserva.be/plantationsample](https://reserva.be/plantationsample)）、本サイトは「予約締切: 開始 60 分前まで / Bookings close 60 minutes before the start time」と明記する。リードタイムは既定 60 分（Cal.com の 120 分例より短く、HPB の締切分数は非公開、`settings` で変更可）、先行予約上限 60 日。タイムゾーンは店舗の Asia/Tokyo に固定し、EN 表示では各時刻の近くに「JST」を明記、端末 TZ への変換はしない。24:00 表記は英語話者に不自然なので、枠は開始–終了併記（23:00–24:00 / 11:00 PM–12:00 AM）で誤解を減らす。

### 氏名は 1 フィールド、ふりがなはひらがな受付で EN では非表示、電話は `type="tel"` 単一欄

GOV.UK は可能な限りフルネーム 1 フィールドを推奨し（[GOV.UK: Names](https://design-system.service.gov.uk/patterns/names/)）、電話番号は「余分なスペース・ハイフン・括弧を許容し国番号にも対応」「例示の有無でエラー文を変える」とする（[GOV.UK: Phone numbers](https://design-system.service.gov.uk/patterns/phone-numbers/)）。Baymard は iOS の電話キーパッドで括弧やダッシュが入力できないため電話番号にそれらを必須にしてはならず、1 つの入力実体を複数フィールドに分割すると摩擦が増えると警告している（[Baymard: Touch keyboard types](https://baymard.com/labs/touch-keyboard-types)、[Avoid splitting single input entities](https://baymard.com/blog/mobile-form-usability-single-input-fields)）。ハイフン許容時は見た目が似た記号（‐ ‑ ‒）の混在を正規化する必要がある（[Zenn: 電話番号のハイフン問題](https://zenn.dev/koakuma_ageha/articles/6d87178b738308)）。ふりがなについて重要なのは、**Chrome が 2026 年 4 月からふりがな欄の自動保存・入力に対応し、判定は「autocomplete 属性（最重視）・ラベル文言・name 属性」のヒューリスティックで、標準外の autocomplete 値を付けると自動入力が効かなくなる**という点である。有効な `name` 値は `full-name-phonetic` / `family-name-phonetic` / `given-name-phonetic`、ラベルは「セイメイ／せいめい／フリガナ（フルネーム）」「セイ／せい／姓ふりがな」「メイ／めい／名ふりがな」が認識され、**Chrome はラベルにカタカナが 1 文字以上含まれていればカタカナ、含まれなければひらがなで入力する**（[Chrome Developers: Japanese phonetic name autofill](https://developer.chrome.com/blog/japanese-phonetic-name-autofill?hl=ja)、2026-04-15 公開、[09_gap_legal_process_ux.md](../research_notes/美容師予約サイト制作ナレッジ/09_gap_legal_process_ux.md) C-3）。カタカナ強制は紙申込書の名残でスマホでは変換が難しいという国内意見が複数あり（[note](https://note.com/ushiwoi/n/n00d65b50619a)、[アテンド](https://www.attend.jp/desine_170317)）、web.dev はプレースホルダをラベル代わりにせずラベルを上に置くよう求める（[web.dev: Sign-in form best practices](https://web.dev/articles/sign-in-form-best-practices)）。

推奨マークアップは、氏名 `<input name="name" autocomplete="name" autocapitalize="off" autocorrect="off">`、ふりがな `name="full-name-phonetic"`（Chrome の判定対象となる標準 name 値）・ラベル「ふりがな」（ひらがな表記のラベルなのでひらがなで自動入力される）・ひらがな受付（カタカナも正規化して受理）・標準外の autocomplete 値は付けない、電話 `<input type="tel" inputmode="tel" autocomplete="tel">` 単一欄で全角・ハイフン・類似ダッシュを正規化後に E.164 で検証、備考 `<textarea>` 任意・文字数上限明示。EN ロケールではふりがな欄を描画せず、氏名は "Full name"、電話は国番号付きも受け付ける。職業「学生/社会人」はラジオ 2 択で、GOV.UK の「なぜ聞くのかを把握する」原則に従い「学生料金の判定に使用 / Used to apply the student rate」を添える。学割はメニューカードに「一般 ¥X / 学生 ¥Y」を併記し、職業選択後の要約と確認画面で適用価格を再計算して表示することで、Heritage 型の「枠選択前に価格が見える」原則と矛盾させない。必須フィールドは「メニュー・氏名・ふりがな・職業・電話・日・時」の 7 つで、Baymard の 2024 年平均（5.1 ステップ・11.3 フィールド、「総フィールド数がステップ数より重要」）を下回る（[Baymard: Average checkout](https://baymard.com/blog/checkout-flow-average-form-fields)）。これ以上は増やさない。

### 完了画面は唯一の証憑なので、1 画面に収めて ICS とキャンセルリンクを置く

メール/SMS を送らない本件では完了画面が唯一の予約証憑になる。確認画面は GOV.UK の Check answers（全回答を一覧し各行から修正）に従い（[GOV.UK: Check answers](https://design-system.service.gov.uk/patterns/check-answers/)）、確定ボタン直上にキャンセルポリシー要点を再掲、文言は「この内容で予約を確定する / Confirm booking」とする。完了画面はスマホ縦 1 画面に、予約番号・日付（曜日）・開始–終了・メニュー・適用料金・店名・住所（地図リンク）・担当者名のカードを収め、「この画面をスクリーンショットで保存してください（確認メールは送信されません）」を日英で明示する。ユーザーが確認画面を後で見返すためにスクリーンショットで保存する行動は観察されている（[Impress Watch](https://www.watch.impress.co.jp/aquosphone/2013/09/130910.html)）。「カレンダーに追加」は Cal.com が Google/Office/Outlook/ICS の 4 リンクを返す形に倣い（[Cal.com API](https://cal.com/docs/api-reference/v2/bookings/get-add-to-calendar-links-for-a-booking.md)）、ICS の `DESCRIPTION` にキャンセル URL を完全な文字列で入れる（インポート時にリンク化されない、[Timify](https://www.timify.com/en/support/6086959-ics-file-customisation/)）。ICS には `VALARM`（前日・1 時間前）を含め、自動リマインドの不在を補う。折りたたみやカルーセルなどスクショで情報が欠ける部品は完了画面で使わない。予約番号とキャンセル URL には「コピー」ボタンを付ける。

キャンセルリンクは `/{locale}/cancel/{token}` のマジックリンク型で、開くと「予約内容の再表示 → 『この予約をキャンセルする』→ 確認ダイアログ → 完了」の 3 段にし（NN/g は取り消しにくい操作前の確認ダイアログを有効とする、[NN/g: Confirmation dialog](https://www.nngroup.com/articles/confirmation-dialog/)）、変更は「キャンセル後に再予約」で足りる。ステートフル方式は発行済みトークンを取り消せる（[tatsuya.website](https://tatsuya.website/ja/magic-links/)）。日本では「予約を忘れた経験がある人 18.8%」で美容院は予約忘れが多い業態とされ（[linestep.jp](https://linestep.jp/2024/01/16/booking-cancel/)）、弁護士はキャンセルポリシーの明文化を勧める（[弁護士ドットコム](https://www.bengo4.com/c_18/n_16198/)）。SMS リマインドの効果（60〜95% 減）はすべてベンダー/自己申告なので（[Salon Business UK](https://www.salonbusiness.co.uk/?p=34226)、[Kapow](https://www.kapow.co.uk/download.html?id=1537)）引用しない。対照群つきの研究は医療機関のものに限られ、Cochrane レビュー（8 RCT・6,615 人）は SMS リマインドで出席率 RR 1.14（95%CI 1.03–1.26、67.8%→78.6%）、電話リマインドと同等（RR 0.99）、コストは電話比 55〜65% 低いと報告している（[Cochrane CD007458](https://doi.org/10.1002/14651858.CD007458.pub3)）。サロン業態の対照研究や日本の美容室無断キャンセル率の業界統計は存在しないため、計画書では「医療 RCT の出席率 +10 ポイント前後を参考値、自店の実測値をベースライン」と注記する。

### アクセシビリティと多言語は WCAG 2.2 の新基準 4 つと「自動リダイレクトしない」で決まる

WCAG 2.2 で追加された AA/A 基準のうち予約フォームに直結するのは、2.5.8 Target Size（24×24 CSS px）、2.4.11 Focus Not Obscured、3.3.7 Redundant Entry（同一プロセス内で再入力させない）、3.3.8 Accessible Authentication である（[W3C: What's New in WCAG 2.2](https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/)）。日付グリッドは APG の Date Picker Dialog に倣い `<table role="grid">` と roving tabindex、Esc で閉じてボタンへフォーカス復帰（[W3C APG: Date Picker Dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/examples/datepicker-dialog/)）、時間枠は**ネイティブ `<input type="radio">` を `fieldset/legend`（「開始時刻を選択 / Choose a start time」）で囲み CSS でボタン風に見せる**のが最も a11y 負債が少ない（[W3C APG: Radio group](https://www.w3.org/WAI/ARIA/apg/patterns/radio/examples/radio/)）。各セルの accessible name は「10月12日(日) 空きあり / Sun, Oct 12, available」のように状態を含める。言語切替は Smashing Magazine が「自動リダイレクトは助けより苛立ちを生む」「国旗は言語を表さない」とし（[Smashing: Language selector](https://smashingmagazine.com/2022/05/designing-better-language-selector)）、USWDS の 2 言語パターンは相手言語名をネイティブ表記で出す（[USWDS: Two languages](https://designsystem.digital.gov/patterns/select-a-language/two-languages/)）。**採用案はヘッダー右上に「EN / 日本語」、初期値は `Accept-Language`、選択は Cookie に保存、自動リダイレクトなし**。KPI は GA4 相当のイベント（form_start / form_submit）で段階別離脱率を取り、良好なフォームの離脱率目安「1% 未満」（[Gyro-n](https://www.gyro-n.com/column/efo-form-analytics-01/)）を理想値にする。

## Next.js 16.4・Neon・排他制約・next-intl・Better Auth で技術構成を確定する

### Server Action で予約を書き、空き枠は `"use cache"` せず Suspense 配下で読む

2026-10-10 時点の安定版は **Next.js 16.4.0**（[npm: next](https://www.npmjs.com/package/next)）で、Node.js 20.9 以上・TypeScript 5.1 以上を要求し、Turbopack が既定、`middleware.ts` は **`proxy.ts` に改名されて Node.js ランタイム固定**、ルートセグメントの `runtime: 'edge'` は deprecated になった（[Next.js docs: Upgrading to v16](https://nextjs.org/docs/app/guides/upgrading/version-16)、[runtime](https://nextjs.org/docs/app/api-reference/file-conventions/route-segment-config/runtime)）。したがってランタイムは全面 Node で統一し、TCP ドライバの制約を気にしなくてよい。予約送信は Server Action が既定で、「POST のみ」「Origin と Host を比較して不一致なら中断」「UI 経由だけでなく直接 POST でも到達可能なので各アクション内で認証・認可・検証を再実施」という公式原則に従う（[Next.js docs: Data Security](https://nextjs.org/docs/app/guides/data-security)、[Mutating Data](https://nextjs.org/docs/app/getting-started/mutating-data)）。Route Handler は Vercel Cron・ICS ダウンロード・将来の Webhook に限定し、キャンセルリンクは GET で副作用を起こさず、ページ表示後の Server Action で実行する。

キャッシュ方針は Cache Components の仕様から導ける。`"use cache"` のランタイムキャッシュは既定でインメモリ LRU であり、「サーバーレスではキャッシュエントリは通常リクエスト間で持続しない」と明記されている（[Next.js docs: use cache](https://nextjs.org/docs/app/api-reference/directives/use-cache)）。また「DB など非同期ソースから毎回新鮮なデータが必要なコンポーネントには `"use cache"` を使わず `<Suspense>` でラップせよ」とあり、`seconds` プロファイルや `expire` 5 分未満は短命キャッシュとしてプリレンダーから除外される（[Caching](https://nextjs.org/docs/app/getting-started/caching)、[Revalidating](https://nextjs.org/docs/app/getting-started/revalidating)）。**採用案: 空き枠コンポーネントはキャッシュせず `<Suspense fallback={<SlotsSkeleton/>}>` 配下でリクエスト時に DB を読む。メニュー一覧・営業時間テンプレートは `"use cache"` + `cacheTag('menus')` + `cacheLife('days')` とし、管理の Server Action で `updateTag('menus')`（Server Action 専用・即時失効）を呼ぶ**（[updateTag](https://nextjs.org/docs/app/api-reference/functions/updateTag)）。`refresh()` はタグ付きデータを再検証しない点に注意する。Proxy の責務は next-intl のロケール判定と `/admin` の Cookie 有無チェック（楽観）に限定し、「Server Function は使用されたルートへの POST として扱われ、matcher で除外されたパスの呼び出しは素通りする」ため認可は必ずアクション内で行う（[proxy.js](https://nextjs.org/docs/app/api-reference/file-conventions/proxy)）。

### ホスティングは Vercel Pro（東京）を第一候補、Cloudflare Workers Paid を代替にする

規約上、Vercel Hobby は本番に使えない（本案件の扱いは本節末尾の決定を参照）。Fair Use Guidelines（2026-09-14 更新）は「Hobby teams are restricted to non-commercial personal use only. All commercial usage of the platform requires either a Pro or Enterprise plan.」と定め、商用の定義に「Advertising the sale of a product or service」「Receiving payment to create, update, or host the site」を含む（[Vercel: Fair Use Guidelines](https://vercel.com/docs/limits/fair-use-guidelines)、[Hobby Plan](https://vercel.com/docs/plans/hobby)）。営業中の美容室のサービス予約サイトを受託制作する本件はこの両方に該当する。**採用案: Vercel Pro（$20/月、1 席・$20 分の利用クレジット付き、hnd1 東京リージョン）**。理由は Next.js 16 の `proxy.ts`・Cache Components・Server Actions・`after()`・毎分 cron・Node `crypto` を使う Web Push 送信の互換性リスクを事実上ゼロにできる唯一の選択肢であり、Pro にすると同時に関数 800s・ランタイムログ 1 日・cron 毎分精度・WAF ルール 40 本・任意デプロイへの Instant Rollback・Cold start prevention が付くためである（[Pro Plan](https://vercel.com/docs/plans/pro)、[09_gap_hosting_alternatives.md](../research_notes/美容師予約サイト制作ナレッジ/09_gap_hosting_alternatives.md)）。数百 PV/日なら従量分（Function Invocations $0.60/1M、Active CPU $0.128/時）は $20 クレジット内に収まり、Spend Management の上限は低めに設定する。**代替: Cloudflare Workers Paid（$5/月）＋`@opennextjs/cloudflare` 1.20.x**。月額を 1,000 円未満に抑える必要がある場合に採り、着手前に①`proxy.ts` 込みの本番ビルドと Turnstile・Server Actions・`after()` の `wrangler dev` 動作、②`web-push` の VAPID 署名・暗号化が `nodejs_compat` で動くこと、③Images binding の `next/image`（Free 5,000 変換/月）、④Neon を Hyperdrive 経由か HTTP ドライバか、⑤DNS を Cloudflare に移管できるか、の 5 点を 1 日で検証する（`proxy.ts` 対応は 1.20.3 以降の experimental、Cloudflare 公式は vinext（beta）を既定推奨に切り替えており中期的な保守リスクがある）。**Workers Free は不採用**: SSR 1 回あたり CPU 10 ms の上限は公式が「SSR … typically use 10-20 ms」と述べる水準で Error 1102 が常態化しうるうえ、cron はアカウント合計 5 本・サブリクエスト 50/回で Push 送信設計を縛る（[Workers Limits](https://developers.cloudflare.com/workers/platform/limits/)）。**次点: Google Cloud Run（asia-northeast1）**はアダプタ不要で互換リスクが最小だが、独自ドメインが preview の domain mapping か Firebase Hosting/外部 LB を要し、Dockerfile・IAM・Scheduler を 1 人で組む運用負荷が本件の規模に見合わない。Netlify Free（300 credits、デプロイ 15 credits/回で枯渇すると全プロジェクト停止、関数は米国実行）、Render Free（公式が本番利用を否定、日本リージョンなし）、Railway（実質無料枠なし）、共用レンタルサーバー（Node.js 非対応）は候補外。

**本案件の決定（開発者の最終判断、2026-10-10）**: 上記の推奨は有償の受託案件を前提にしたものである。本案件は友人のための無償制作であるため、開発者は Phase 1 本番を Vercel Hobby で運用すると判断し、「Advertising the sale of a product or service」も商用に含むという規約上のリスク（警告・停止）は開発者・クライアントが了承した。Vercel から警告・停止があった場合は Vercel Pro または Cloudflare Workers Paid へ移行し（`SITE_URL` によるドメイン非依存設計で環境変数と DNS の切替に留める）、紹介案件など有償案件では最初から Pro を使う。

### DB は Neon Free を Vercel Marketplace から入れ、Supabase はチャットを早期化する場合の代替にする

Vercel Postgres は終了し、既存 DB は 2024 年 12 月に Neon へ自動移行、`@vercel/postgres` は npm で deprecated 表示になっている（[npm: @vercel/postgres](https://www.npmjs.com/package/@vercel/postgres)）。Neon の Vercel-Managed Integration は Marketplace から導入でき、請求は Vercel に統合、`DATABASE_URL` が自動注入され Preview Deployment ごとに DB ブランチを作れる（[Neon docs: Vercel-Managed Integration](https://neon.com/docs/guides/vercel-managed-integration)）。Neon Free（公式 docs 2026-10-06 更新）は**コンピュート 100 CU-hours/プロジェクト（0.25 CU で 400 時間/月）、5 分無操作でスケール to ゼロ（無効化不可）、ストレージ 1 GB/プロジェクト・アカウント合計 20 GB、履歴 6 時間、スケジュールバックアップなし**で、再開は数百ミリ秒かかる（[Neon docs: Plans](https://neon.com/docs/introduction/plans)、[Scale to Zero](https://neon.com/docs/introduction/scale-to-zero)）。第三者サイトが記す Free 0.5 GB（[jetadmin.io](https://www.jetadmin.io/blog/neon-pricing/)）は旧情報で、公式 Plans ページと pricing ページのバナー「now with 1 GB of Postgres storage per project」で 1 GB を確認済み。Supabase Free は **DB 500 MB・Nano 共有 CPU・1 週間無通信で一時停止（警告メールが約 1 週間前に届き、Dashboard の「Resume project」で 1 年以内なら復旧可。「週に数件/日程度の DB クエリ」があれば回避）・自動バックアップなし**だが Realtime（同時接続 200、月 200 万メッセージ）・Auth（50,000 MAU）・Storage 1 GB が同梱される（[supabase plans.ts](https://github.com/supabase/supabase/blob/master/packages/shared-data/plans.ts)、[Realtime Limits](https://supabase.com/docs/guides/realtime/limits)）。PlanetScale は無料枠終了、Turso は SQLite で範囲型・排他制約が使えない（[cloudinsight.cc](https://cloudinsight.cc/en/blog/free-cloud-database)）。

**採用案: Phase 1 は Neon Free**。理由は pause がなく無人運用に強いこと、1 GB は予約データなら数年分、コールドスタート数百 ms は Suspense で吸収できること、素の Postgres なので `btree_gist` + `EXCLUDE` が使えることである。顧客チャットを早期に出す決定をした場合のみ Supabase に切り替える。どちらも素の Postgres なので SQL マイグレーションで管理しておけば `pg_dump`/`pg_restore` で相互移行でき、Supabase 固有機能（RLS、Realtime publication）は `/lib/db` の後ろに隠す。コスト段差は Neon Launch が従量（$0.106/CU-hour、$0.35/GB-month、月額最低なし）、Supabase Pro が $25/月（日次バックアップ 7 日付き）である。

### 二重予約は `EXCLUDE USING gist (resource_id WITH =, during WITH &&)` で最終防衛する

PostgreSQL は「範囲型には UNIQUE より排他制約が適切」とし、`EXCLUDE USING GIST (during WITH &&)` に重なる行を INSERT すると `conflicting key value violates exclusion constraint` になる（[PostgreSQL docs: Range Types](https://www.postgresql.org/docs/current/rangetypes.html)）。スカラー等値（`resource_id WITH =`）を混ぜるには `btree_gist` が必要で、これは trusted 拡張なのでスーパーユーザー権限なしで `CREATE EXTENSION` できる（[btree_gist](https://www.postgresql.org/docs/current/btree-gist.html)）。`CREATE TABLE` 構文は `EXCLUDE … WHERE (predicate)` の部分排他制約を許す（[CREATE TABLE](https://www.postgresql.org/docs/current/sql-createtable.html)）。エラーコードは `23P01 exclusion_violation`、`23505 unique_violation`、`40001 serialization_failure` である（[errcodes.txt](https://github.com/postgres/postgres/blob/master/src/backend/utils/errcodes.txt)）。開始時刻だけの UNIQUE は所要時間が可変になったとき 18:00–19:30 と 19:00 の衝突を防げず、check-then-insert は競合する（[dev.to](https://dev.to/usamacheema453/how-to-prevent-double-bookings-in-nextjs-race-conditions-db-constraints-2cj9)）。Cal.com の Prisma スキーマは `idempotencyKey @unique`（「slot start/end & email に基づく UID」）を持つがスキーマ内に `EXCLUDE` は存在せず、衝突判定はアプリ側 `checkForConflicts` で行っている（[calcom schema.prisma](https://github.com/calcom/cal.com/blob/main/packages/prisma/schema.prisma)、[checkForConflicts.ts](https://github.com/calcom/cal.com/blob/main/packages/features/bookings/lib/conflictChecker/checkForConflicts.ts)）。本件は DB 制約で Cal.com より強い保証を得られる。

設計書に転記する DDL の要点は次のとおり。`bookings(id uuid, resource_id smallint default 1, menu_id, during tstzrange, status check in ('confirmed','arrived','in_progress','completed','cancelled_by_customer','cancelled_by_owner','cancelled_late','no_show'), source check in ('web','phone','walk_in','instagram','admin'), idempotency_key text unique, …)` に、半開区間を強制する `check (lower_inc(during) and not upper_inc(during))` と、**`exclude using gist (resource_id with =, during with &&) where (status in ('confirmed','arrived','in_progress'))`** を付ける。`WHERE` によりキャンセル済み行は制約対象外になり同じ枠を再予約でき、半開区間 `[)` で 19:00 終了と 19:00 開始が衝突しない。`resource_id` を持たせると将来の 2 席化が DDL 変更なしで済む。トランザクションは既定の READ COMMITTED のままでよく、並行 INSERT は GiST で衝突して片方が `23P01` で失敗するので `SELECT … FOR UPDATE` や SERIALIZABLE（`40001` の再試行ループが必要、[Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html)）は 1 席規模では不要である。Server Action は `23P01` を `slot_taken`（「その枠はたった今埋まりました」＋枠再取得）、`23505` を「同一人物の二重送信」として既存予約を返す写像にし、冪等性キーは `sha256(slotStart|menuId|phone)` から決定的に作る。`time_blocks` は別テーブルなので DB 制約では相互排他できず、ブロック作成時に同一トランザクション内で confirmed 予約の有無を確認し、空き枠生成側でブロック区間を除外する。厳密化したければ両者を `calendar_items(kind, during)` に統合して 1 本の排他制約で守る。

### 空き計算は「JST で候補生成 → UTC の tstzrange → `&&` で除外」を SQL 一発で行う

データモデルは `menus(duration_min, buffer_after_min, price_jpy, price_student_jpy, name_ja/en)`、`business_hours(weekday, is_closed, open_min, close_min)`（月曜定休は `weekday=1, is_closed=true`、18:00–24:00 は 1080–1440）、`business_hour_overrides(date, …)`、`time_blocks(during, reason)`、`settings(slot_step_min=30, lead_time_min=60, max_advance_days=60, timezone='Asia/Tokyo')` に分ける。候補枠は `generate_series(open_min, close_min - duration - buffer, step)` で分単位に生成し、`(date::timestamp + make_interval(mins => m)) at time zone 'Asia/Tokyo'` で `timestamptz` に変換、`NOT EXISTS (bookings/time_blocks WHERE during && tstzrange(start, start + duration + buffer, '[)'))` で除外する。上限を `close - duration - buffer` にすることで閉店をまたぐ枠を出さない。Cal.com も最小通知を `now + minimumBookingNotice` として切り上げ、全計算にタイムゾーンを通している（[calcom slots/util.ts](https://github.com/calcom/cal.com/blob/main/packages/trpc/server/routers/viewer/slots/util.ts)）。日本は夏時間がなく Asia/Tokyo は常に +09:00 だが、固定オフセットをハードコードせず IANA 名を使う。クライアントの `new Date(y, m, d, h)` はブラウザのローカル TZ で解釈されるため海外ユーザーで壊れる。**フォームは ISO 文字列（`2026-11-03T18:00:00+09:00`）を hidden で送り、サーバーで Zod の `z.iso.datetime({ offset: true })` で受け、`lead_time`/`max_advance`/営業時間を Server Action 側でも再検証する**（UI のグレーアウトは直接 POST で突破されうる）。日付ライブラリは Temporal が Stage 4 で Chrome 144・Firefox 139・Node 26 に出荷済みだが Safari 未出荷のため（[tc39/proposal-temporal](https://github.com/tc39/proposal-temporal)）、`temporal-polyfill`（19.5 kB、[npm](https://www.npmjs.com/package/temporal-polyfill)）か `date-fns` v4 + `@date-fns/tz` を選ぶ。採用は `temporal-polyfill`（将来ポリフィルを外すだけ）とし、ADR に残す。

### i18n は next-intl 4、`localePrefix: 'always'`、`timeZone: 'Asia/Tokyo'` で固定する

next-intl は 4.14.9（2026-10-02）で CHANGELOG に Next.js 16 対応と 16.3 互換準備が記載され（[next-intl CHANGELOG](https://github.com/amannn/next-intl/blob/main/packages/next-intl/CHANGELOG.md)）、`proxy.ts` の `createMiddleware(routing)` がロケール交渉・リダイレクト・hreflang を担い、検出順は「パス → `NEXT_LOCALE` Cookie → `accept-language` → defaultLocale」である（[next-intl docs: Proxy](https://next-intl.dev/docs/routing/middleware)）。`@inlang/paraglide-next` は npm で deprecated（paraglide-js 2 を直接使い Next.js アダプタ不要）であり（[npm](https://www.npmjs.com/package/@inlang/paraglide-next)）、next-i18next は Pages Router 時代の設計のため、二言語・小規模では next-intl の統合コストの低さが勝つ。**採用案**: `defineRouting({ locales: ['ja','en'], defaultLocale: 'ja', localePrefix: 'always' })`、matcher `['/((?!api|_next|_vercel|.*\\..*).*)']`、`/admin` は matcher から除外して日本語固定、`generateStaticParams` でトップ・メニューを静的化、`alternateLinks` は有効のまま。`localePrefix: 'as-needed'` は既定ロケールで接頭辞が消え、キャンセル URL など絶対 URL 生成でロケール判定が絡むので採らない。`getRequestConfig` で `timeZone: 'Asia/Tokyo'` と `formats.dateTime.slot = { month:'numeric', day:'numeric', weekday:'short', hour:'2-digit', minute:'2-digit', hour12:false }` を定義し、「11/3(火) 18:00」「Tue, 11/3, 18:00」を同一コードで出す（[next-intl docs: Configuration](https://next-intl.dev/docs/usage/configuration)）。Server Action のエラー文は `next-intl/server` の `getTranslations` と Zod の contextual error map でロケール別に返す（[next-intl docs: Server Actions](https://next-intl.dev/docs/environments/actions-metadata-route-handlers)）。Zod 4 は `z.config(ja())` で日本語ロケールを持つ（[zod ja.ts](https://github.com/colinhacks/zod/blob/main/packages/zod/src/v4/locales/ja.ts)）。

### 管理者 1 名の認証は Better Auth + パスキー、キャンセルトークンは 256 bit をハッシュ保存する

Auth.js の README は「Auth.js は Better Auth の一部になった。新規プロジェクトは Better Auth で始めることを推奨」と明記し、v5 は依然 beta（5.0.0-beta.32）、WebAuthn プロバイダは experimental で本番非推奨である（[nextauthjs/next-auth README](https://github.com/nextauthjs/next-auth)、[authjs.dev: WebAuthn](https://authjs.dev/getting-started/authentication/webauthn)）。Better Auth 1.7.7 は Passkey（SimpleWebAuthn ベース）と Magic Link をプラグインで提供し、「proxy ではセッション Cookie の存在確認のみ」を推奨する（[Better Auth docs: Next.js](https://www.better-auth.com/docs/integrations/next)、[Passkey](https://www.better-auth.com/docs/plugins/passkey)）。Next.js 公式も自前実装より認証ライブラリを推奨し、最小構成なら `iron-session`/`jose` を挙げる（[Next.js docs: Authentication](https://nextjs.org/docs/app/guides/authentication)）。**採用案: Better Auth（Postgres アダプタ）+ `passkey()` を主、`magicLink()`（Resend 経由）をフォールバック、`signUp` は環境変数で無効化し初回は seed で作成**。パスキーは iCloud キーチェーンで同期され機種変更に強く、PWA 内で Face ID ログインが可能で、WCAG 3.3.8 も自然に満たす。Cookie は `__Host-` 接頭辞・`HttpOnly; Secure; SameSite=Lax`・`Max-Age` 30 日のローリング更新、サーバー側 `sessions` テーブルに端末一覧と「この端末以外をログアウト」を持つ。

キャンセルトークンは OWASP の「CSPRNG で生成、単回使用、適切な期間で失効、ブルートフォースにレート制限」「ストアの読み取り漏洩が脅威なら一方向ハッシュを保存、128 bit 以上・推奨 160 bit 以上」に従い（[OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)、[Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)）、`randomBytes(32).toString('base64url')`（43 文字）を URL に載せ、DB には `cancel_token_hash bytea unique`（SHA-256）のみ保存、`timingSafeEqual` で照合、形式 `^[A-Za-z0-9_-]{43}$` で早期拒否する。有効期限は `lower(during) - 2 時間`（セルフキャンセル締切）とし、期限後は「お電話ください」（`tel:` リンク）に切り替える。レート制限は `/cancel/[token]` に IP 10 回/分、`createBooking` に IP 5 回/10 分＋同一電話番号 3 件/日。`@upstash/ratelimit` は HTTP ベースでサーバーレス向け（[upstash/ratelimit-js](https://github.com/upstash/ratelimit-js)）だが、追加サービスを避けるなら Postgres の `rate_limits(key, window_start, count)` でも足りる。

### 監視・バックアップ・ドメイン移行は無料枠の弱点を GitHub Actions と `SITE_URL` で埋める

無料枠で最大の弱点はバックアップである。Supabase Free は自動バックアップなし、Neon Free は履歴 6 時間＋手動スナップショット 1 つで、どちらもスケジュールバックアップは有料（[Supabase docs: Backups](https://supabase.com/docs/guides/platform/backups)、[Neon docs: Plans](https://neon.com/docs/introduction/plans)）。**採用案: GitHub Actions で日次 `pg_dump --format=custom` を実行し暗号化して 30 世代保存**（パブリックリポジトリは Actions 無料、[GitHub Docs](https://docs.github.com/en/billing/concepts/product-billing/github-actions)）。Vercel Cron で代替しないのは、関数内で `pg_dump` を実行して外部ストレージへ暗号化保存する構成が GitHub Actions より煩雑であり、Hobby（本案件の Phase 1 本番）では cron が **1 日 1 回・時間精度 ±59 分・UTC・best effort**（Pro は毎分精度、全プラン 100 ジョブ/プロジェクト）だからである（[Vercel docs: Cron jobs](https://vercel.com/docs/cron-jobs/usage-and-pricing)）。エラー監視は Sentry の無料 Developer プランで、全プランに cron モニタ 1・uptime モニタ 1 が含まれる（[Sentry docs: Pricing](https://docs.sentry.io/pricing/)）。重要イベント（予約作成/キャンセル/手動変更）は `bookings_audit` に DB 記録してログ保持に依存しない。独自ドメイン移行は Vercel の Domains で apex は A レコード `76.76.21.21`、サブドメインは CNAME `cname.vercel-dns-0.com`、`www` を主にして apex をリダイレクトする構成が推奨される。自動リダイレクトされるのは www あり/なしの間だけで、`*.vercel.app` から新ドメインへは Domains → Edit → 「Redirect to」で**手動設定**する（CNAME 値はプロジェクトごとに固有なのでダッシュボード表示値を正とする。[Vercel docs: Add a domain](https://vercel.com/docs/domains/working-with-domains/add-a-domain)、[Deploying and redirecting](https://vercel.com/docs/domains/working-with-domains/deploying-and-redirecting)）。レート制限は Vercel WAF の Rate Limiting が全プランで使え（Hobby 1 ルール、Pro 40 ルール、固定窓 10 秒〜10 分、1M allowed requests/月同梱）、`/cancel/[token]` と予約作成への IP 単位の粗い制限は WAF、同一電話番号の回数制限などキー付き制御はアプリ側（Postgres `rate_limits`）の二段構えにする（[Vercel WAF: Rate Limiting](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting)）。`NEXT_PUBLIC_` 変数はビルド時にインラインされ後から変えられないため（[Next.js docs: Environment Variables](https://nextjs.org/docs/app/guides/environment-variables)）、サイト URL は**サーバー専用の `SITE_URL`** として持ち、DB には相対パスだけを置いて表示時に `absoluteUrl()` で組み立てれば、ドメイン移行後も過去予約のキャンセルリンクが新ドメインで表示できる。

## iOS のプッシュは「ホーム画面追加・毎回通知表示・起動時再確認」で成立する

### iOS 16.4 以降の要件と 2026 年時点の既知の落とし穴

MDN の browser-compat-data によれば `PushManager.subscribe()` は Safari iOS 16.4 で追加され「ホーム画面に保存したウェブアプリでのみ通知をサポート」、`Notification` はホーム画面アプリかつ**マニフェストの `display` が `browser` 以外**でなければ undefined で、通知は Service が一度だけコピーされ（[progressier.com](https://progressier.com/pwa-capabilities/cookies-demo)）、セッション Cookie がランダムにリセットされる回帰バグ [WebKit 272325](https://bugs.webkit.org/show_bug.cgi?id=272325) は **2026-10 時点でも Status NEW（未修正）**で iOS 18.1 でも再現報告がある（永続 Cookie では再現しない）。また iOS 設定で通知を OFF にしても `Notification.permission` が `"default"` を返す（[WebKit 320551](https://bugs.webkit.org/show_bug.cgi?id=320551)）、APNs が 201 を返しても端末に届かない（[WebKit 319865](https://bugs.webkit.org/show_bug.cgi?id=319865)）、再起動後に `getSubscription()` が null になっても旧エンドポイントに 410 が返らない（[WebKit 284111](https://bugs.webkit.org/show_bug.cgi?id=284111)）といったバグも NEW のまま残っている。**採用案**: オンボーディングは「ホーム画面に追加 → アイコン起動 → アプリ内でログイン → 設定の『通知をオンにする』をタップ → `requestPermission()` → `subscribe()`」の一本道にし、Safari タブで開いている場合（`display-mode: standalone` でない）は購読 UI を出さず追加手順を図解する。起動のたびに `getSubscription()` を確認し、null なら再購読バナー、非 null なら `last_seen_at` を更新する。SW の `push` ハンドラは例外なく `event.waitUntil(showNotification(...))` を呼び、通知は「タイトル＋本文＋`data.url`」の最小構成（電話番号は含めない）にする。Cookie は `Max-Age` 明示の永続 Cookie を**必須**とし、セッション Cookie（有効期限なし）を使わない（272325 が未修正のため）。起動時チェックは `Notification.permission` を信用せず「`getSubscription()` が null か」を主条件にし、`requestPermission()` がダイアログを出さない/`granted` 以外を返す場合は「設定 > 通知 > <アプリ名>」への案内を出す。通知が届かない問い合わせの一次切り分けは「集中モード/おやすみモード → 設定 > 通知 → アイコンから起動しているか → iOS バージョン」の順（[Apple Forums 770749](https://developer.apple.com/forums/thread/770749)）。

### 実装は `app/manifest.ts` + 手書き最小 SW + `web-push`、Serwist は後付けにする

Next.js 公式ガイドは `app/manifest.ts`、`navigator.serviceWorker.register(..., { scope: '/', updateViaCache: 'none' })`、`pushManager.subscribe({ userVisibleOnly: true, applicationServerKey })`、Server Action からの `webpush.sendNotification`、`npx web-push generate-vapid-keys`、SW の `push`/`notificationclick` 例、`/sw.js` への `Cache-Control: no-cache` と CSP を示している（[vercel/next.js progressive-web-apps.mdx](https://github.com/vercel/next.js/blob/canary/docs/01-app/02-guides/progressive-web-apps.mdx)）。ライブラリは `serwist`/`@serwist/turbopack` 9.5.13（2026-10-04、Next 16/Turbopack 対応）が現行で、`next-pwa` 5.6.0 は 2022 年、`@ducanh2912/next-pwa` は 2024 年で更新停止し Serwist への移行を促している（[registry: @serwist/turbopack](https://registry.npmjs.org/@serwist/turbopack)、[next-pwa](https://registry.npmjs.org/next-pwa)、[@ducanh2912/next-pwa](https://registry.npmjs.org/@ducanh2912/next-pwa)）。`web-push` 3.6.7（2024-01 以降更新なし、`engines.node >= 16`、`package.json` に `"type"` なしの CommonJS だが ESM から default import で利用可）は `TTL`・`urgency`（即時は `high`）・`topic`（32 文字以内、未配信メッセージを置換）・`timeout` を受け、**Safari のエンドポイントは VAPID subject に `https://localhost` を使うと `BadJwtToken` で拒否する**（[web-push README](https://github.com/web-push-libs/web-push/blob/master/README.md)）。404/410 は購読失効のシグナルで DB から削除すべきだが、ライブラリがエラー時に返さないレスポンスに 410 判定をしていて削除が一度も走らなかった事後検証がある（[pushpad.xyz](https://pushpad.xyz/blog/web-push-error-410-the-push-subscription-has-expired-or-the-user-has-unsubscribed)、[dev.to](https://dev.to/tonytonycoder11/the-cleanup-that-could-never-run-a-silent-web-push-leak-in-go-1kaj)）。

**採用案**: 1 人運用ではオフラインキャッシュの価値が低く、SW のバグが push を壊すリスク（iOS は SW 例外で許可取り消し）の方が大きいため、**最初は手書き SW（`push`/`notificationclick`/`pushsubscriptionchange` のみ）**にし、Serwist は必要になってから足す。`push_subscriptions(endpoint unique, p256dh, auth, platform, last_seen_at, last_success_at, fail_count)` を Postgres に持ち、送信は `Promise.allSettled` で `TTL: 6h, urgency: 'high', topic: 'booking-<id>', timeout: 8000`、`WebPushError.statusCode` が 404/410 なら削除。ペイロードは最初から**出荷版 Declarative Web Push の JSON 形**にする。web-push の既定（`Content-Type: application/octet-stream` + `aes128gcm`）のままこの JSON を payload にすれば、iOS 18.4+ では SW を起動せずブラウザが宣言的に表示し、それ以外では SW の `push` ハンドラが `data.notification` を `showNotification()` に転記する。Content-Type の変更は不要であり、そもそも web-push は `headers` オプション適用後に Content-Type を上書きするため変更できない。

```json
{
  "web_push": 8030,
  "notification": {
    "title": "新規予約 14:00 カット（山田様）",
    "body": "10/12(日) 14:00–15:00",
    "lang": "ja",
    "navigate": "https://<domain>/admin/bookings/<id>",
    "tag": "booking-<id>",
    "data": { "bookingId": "<id>", "kind": "created" },
    "app_badge": 3
  },
  "app_badge": 3,
  "mutable": false
}
```

`app_badge` は WebKit trunk がトップレベルを読み、ブログ例は `notification` 内に置くため、実機で効いた側が確定するまで**両方**に入れる（未知キーは無視される）。`mutable` はトップレベルのみ（Safari 26.2 で `notification` 内から外側へ修正）。`tag` は iOS では置換が効かない（Bug 258922/319860 とも NEW）ので同一予約の重複表示を許容し、置換は `topic` に任せる。`notificationclick` では `clients.matchAll({ type: 'window', includeUncontrolled: true })` → 既存ウィンドウがあれば `client.navigate(path)` してフォーカス、なければ `clients.openWindow(path)`、失敗時は `openWindow` にフォールバックし、`client.url` 一致でフォーカスしない（SPA では古いまま、[mdn/content clients/openwindow](https://github.com/mdn/content/blob/main/files/en-us/web/api/clients/openwindow/index.md)）。管理画面は `start_url: '/admin'`・`scope: '/admin'` にして顧客サイトに不要な SW を登録しない。Android Chrome は `beforeinstallprompt`（保持した `prompt()` は 1 回のみ、[web.dev](https://github.com/GoogleChrome/web.dev/blob/main/src/site/content/en/learn/pwa/installation-prompt/index.md)）と manifest の `screenshots`+`description` による richer install UI（[developer.chrome.com](https://developer.chrome.com/blog/richer-pwa-installation)）に対応し、Badging API は非対応だが未読通知があれば OS がバッジを付ける（[mdn/content display_badge](https://github.com/mdn/content/blob/main/files/en-us/web/progressive_web_apps/how_to/display_badge_on_app_icon/index.md)）。VAPID 鍵は一度生成したら固定する。

### 信頼性は「未確認件数バッジ＋可視時ポーリング＋日次サマリー＋オーナー向け二次チャネル」で多層化する

Push 単独に依存しない。`bookings.acknowledged_at` を持ち、管理 PWA のヘッダに「未確認 n 件」を表示、起動時と `visibilitychange` で取得し、可視の間は React Query の `refetchInterval` 20 秒・`refetchOnWindowFocus` で更新する（TanStack Query の既定はフォーカス・再接続で自動再取得、[TanStack Query docs](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)）。Neon は 5 分無操作で停止するため、ポーリング中はコンピュートが起き続ける点を見込む（1 日 10 時間開いても約 75 CU-h で 100 CU-h 内だが余裕は小さい。`refetchIntervalInBackground: false` でタブ非表示時は止まる）。日次サマリー（「明日の予約一覧」）は Vercel Cron を `0 12 * * *`（= 21:00 JST。Pro は毎分精度なので 21:00 ちょうど、本案件の Phase 1 で使う Hobby では ±59 分）で回し、`CRON_SECRET` 照合と `digest_sent_on` による重複防止を入れる。オーナー向け二次チャネルは、LINE Messaging API のコミュニケーションプラン（月 200 通無料、追加購入不可で超過は送信エラー停止。スタンダードは 2026 年 10 月 1 日改定で追加 20 万通まで 3 円/通）か Resend 無料（3,000 通/月・100 通/日・3 ドメイン・データ保持 30 日、Vercel Marketplace から `ap-northeast-1` で作成可）が低コストで、Twilio の日本宛 SMS は約 $0.08–0.089/通と高い（[developers.line.biz](https://developers.line.biz/ja/docs/messaging-api/pricing/)、[lycbiz.com 20261001](https://www.lycbiz.com/jp/news/line-official-account/20261001/)、[resend.com/pricing](https://resend.com/pricing.md)、[twilio.com](https://www.twilio.com/ja/sms/pricing/jp)）。Vercel の関数実行時間は Hobby 300 秒・Pro 既定 300 秒/最大 800 秒なので push 送信（購読 1〜3 件、数秒）は問題ない（[vercel.com/docs/functions/limitations](https://vercel.com/docs/functions/limitations)）。**Hobby は Fair Use で商用不可が確定**しているため、有償案件では本番を Vercel Pro（$20/月）として計画書へ計上する（前節「ホスティングは Vercel Pro…」）。本案件は無償案件のため Phase 1 を Hobby で運用する判断となり（同節末尾）、日次サマリーは Hobby の ±59 分を前提にする。

### ダッシュボードは「今日・週・受信箱・設定」のボトムタブと、2 タップで終わるブロック作成

Square Appointments は時間ブロックを「Personal Event」として `+ → Create Personal Event` で作り「Block Time」が自動オン、顧客の予約ページには表示されない（[squareup.com/help](https://squareup.com/help/gb/article/5533)）。Cal.com Companion は数タップで予約の作成・変更・キャンセルと push 通知を提供する（[apps.apple.com](https://apps.apple.com/ca/app/cal-com/id6757157271)）。**採用案**: `start_url` は「今日」ビュー（18:00–24:00 の縦タイムライン、15 分刻み、現在時刻ライン、カード高さ ≥ 56px、`tel:` リンク、来店済み/キャンセルのスワイプ）、週ビューは 7 列の件数と空き率、FAB「+」は「手動予約」「時間をブロック」の 2 択で、ブロックは「今から 30 分 / 1 時間 / 終日 / 期間指定」のプリセット。手動予約・ブロック作成時はサーバーで重なりを判定し「19:00–20:00 の山田様と重なります」を赤表示して `[それでも保存]`（意図的な重複を許容）と `[時間を変更]` を出す。キャンセル・削除は即時実行＋5 秒の「取り消す」トースト（ソフトデリート＋復元エンドポイント）。standalone ではブラウザの戻るがないので詳細画面に明示的な「←」を置き、`@media (display-mode: standalone)` で判定する（[mdn/content create_a_standalone_app](https://github.com/mdn/content/blob/main/files/en-us/web/progressive_web_apps/how_to/create_a_standalone_app/index.md)）。受け入れテストは iOS 実機で「Safari タブでは案内のみ → 追加 → 起動 → ログイン → 通知オン → テスト通知 → 顧客予約から 10 秒以内に通知 → 端末再起動後も届く → 1 週間後の購読確認 → 機内モードでキャッシュ表示 → 他端末ログアウト」の 9 項目に、一次資料の検証で判明した次の項目を加える: 宣言的通知タップの `navigate` 遷移を「アプリ完全終了／バックグラウンド（端末スリープ後）／前面」の 3 状態で確認（Bug 268797 C38/C39 の「ルートに戻る」現象の有無）、`app_badge` がトップレベル・`notification` 内のどちらで効くか、iOS 設定で通知 OFF → 再起動でアプリ内の設定誘導が出ること（Bug 320551）、「テスト通知」でサーバーの APNs 201 と端末受信を突き合わせ届かなければ購読を作り直す導線（Bug 319865）、アプリを閉じて再度開いてもログイン状態が維持されること（永続 Cookie、Bug 272325 未修正）、バックグラウンド復帰時のリロードでフォーム入力が失われないこと（下書きを `sessionStorage`/`IndexedDB` に保存）。前面表示中の通知バナーは Apple に一次資料がなく実機で確認する。

### テストは空き枠ロジックの契約テストを最多に、二重予約は DB 統合と E2E の 2 層で担保する

### アクセシビリティは WCAG 2.2 AA、日本語は `lang`・`<ruby>`・`autocomplete`・`inputmode` が要点

### セキュリティは「安価な検証を先に」の Server Action テンプレートと OWASP ヘッダーで固める

includeSubDomains; preload`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: strict-origin-when-cross-origin`、`X-Frame-Options: DENY`（CSP `frame-ancestors` 優先）、`Permissions-Policy: camera=(), microphone=(), geolocation=()` を `next.config.ts` の `headers()` に置き（[OWASP HTTP Headers](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html)）、CSP はまず `Content-Security-Policy-Report-Only` で検証してから強制に切り替える（Turnstile の `challenges.cloudflare.com` を許可）。ログは電話番号を書かず（ハッシュ末尾 4 桁）、`error.digest` でサーバーログと突合する（[OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)）。GitHub Actions は SHA ピン留め・`permissions: contents: read`・「書き込み権限者は全シークレットを読める」前提で環境シークレットに必須レビュー（[GitHub Docs: Secure use](https://docs.github.com/en/actions/reference/security/secure-use)）。

日本の要件定義書の定番骨格は「背景・目的／体制・スケジュール／サイト構成／機能要件／非機能要件／リリース要件」で（[lancers.jp](https://www.lancers.jp/c/website/website-knowhow/13103/)）、非機能は IPA 非機能要求グレードの 6 大項目（可用性／性能・拡張性／運用・保守性／移行性／セキュリティ／システム環境）・大項目 6・中項目 35・小項目 118・メトリクス 238 で網羅できるが利用は任意である（[atmarkit](https://atmarkit.itmedia.co.jp/ait/spv/1405/10/news001_4.html)、[zenn.dev](https://zenn.dev/nttdata_tech/articles/c16414c86883cb)）。MoSCoW は MVP を Must のみで構成し、Won't の明文化が後工程のズレを減らす（[pragmaticcoders.com](https://www.pragmaticcoders.com/?p=3880)）。本件の章立ては「1 文書管理 / 2 背景と目的（現状の DM 運用と課題、KPI、用語）/ 3 ユーザーとユースケース（UC-01 空き検索→予約、UC-02 キャンセル、UC-03 手動予約、UC-04 枠ブロック、UC-05 当日運用）/ 4 スコープ（MoSCoW 表、Won't: チャット・カルテ・決済・顧客リマインド）/ 5 機能要件 / 6 非機能要件（6 大項目に各 2〜5 行の目標値）/ 7 データ要件 / 8 外部連携 / 9 画面一覧 / 10 法務 / 11 体制・コミュニケーション計画 / 12 スケジュール・検収基準 / 13 リリース要件 / 14 未決事項・リスク」とし、各 Must に「同一枠への二重予約が発生しない」「予約確定後 10 秒以内に管理 PWA へ通知が届く」のような客観的受け入れ基準を 1 つ以上付ける。本レポートの判断表はそのまま 4〜6 章に転記できる。

### 設計書は `docs/design/` の Markdown＋Mermaid、技術判断は ADR で残す

画面遷移図は「画面名・遷移トリガー操作・画面間の関係」を図にして共通認識に使い（[crexgroup.com](https://crexgroup.com/ja/development/project/screen-transition-diagram-guide/)）、画面仕様書は「どこをどう操作でき、どんな処理が起きるか」まで書く（[biz.moneyforward.com 9028](https://biz.moneyforward.com/work-efficiency/basic/9028/)）。ADR は Nygard 形式（Title/Status/Context/Decision/Consequences）が「simple and popular」で、`adr/` に 1 決定 1 ファイルで積む（[architecture-decision-record](https://github.com/joelparkerhenderson/architecture-decision-record)）。推奨構成は `00_overview.md`（構成図）、`01_sitemap.md`、`02_screen_list.md`（画面 ID・名・URL・権限・機能・対応 WF）、`03_screen_flow.md`（Mermaid flowchart）、`04_screen_spec/`（項目定義・操作→処理・バリデーション・エラー文言・空状態）、`05_er.md`、`06_state.md`（予約: confirmed → arrived → in_progress → completed / cancelled_* / no_show）、`07_api.md`（Server Action と Route Handler の一覧、冪等性）、`08_components.md`、`09_security.md`、`adr/0001-drizzle.md, 0002-temporal-polyfill.md, 0003-better-auth-passkey.md, 0004-turnstile-honeypot-ratelimit.md, 0005-next-intl-locale-prefix.md, 0006-exclusion-constraint.md, 0007-neon-free.md`。予約ドメインで必ず決める事項は、枠の粒度（30 分）、所要時間と枠の関係（60 分固定→可変への移行条件）、同時予約の排他（排他制約）、キャンセル締切（2 時間前）、タイムゾーン・祝日（祝日は休業にせず表示のみ）、複数席の要否（`resource_id` で将来対応）、PWA のオフライン挙動（読み取り専用）である。

### WF はグレースケール 390×844、デザイン提案は「方向性 2〜3 案 → 1 案」、修正は回数と前工程戻りを契約に書く

ワイヤーフレームは構造とレイアウトを優先する低忠実度の設計図で（[miro.com](https://miro.com/ja/wireframe/what-is-a-wireframe/)）、デザインカンプは色・フォント・画像を具体化した完成見本である（[xserver.ne.jp](https://www.xserver.ne.jp/bizhp/homepage-design-comp/)）。クライアントからは「特定の色やフォントに関する意見を求める」ことで好みを引き出し（[book.st-hakky.com](https://book.st-hakky.com/business/what-is-design-comp)）、修正依頼は 1 か所に集約する（[uxpin.com](https://www.uxpin.com/studio/jp/?p=30424)）。修正回数の相場は 2〜3 回で、前工程に戻る修正は別見積とする旨を契約に明記し（[atsoho.com](https://atsoho.com/blog/shuseikaisu-designer)）、約款例では「納入から 14 日以内に検収、期間内に不合格通知がなければ合格みなし」「修正上限 2 回」とされる（[lawinsider.com](https://lawinsider.com/ja/clause/納品検収)）。**採用案**: 忠実度は①紙/FigJam → ②Figma グレースケール 390×844 → ③ベースデザイン 3 画面（トップ／メニュー・空き検索／予約フォーム）→ ④全画面＋管理 PWA 主要画面。第 2 回会議のデザイン提案は**スタイルタイル 2〜3 方向（例: A ヴィンテージ強め、B ミニマル寄り、C 写真主導）＋各トップ 1 画面**に留め、選択後は 1 案に収束し方向転換は変更要求扱い。レビューは「見てほしい観点リスト」を事前配布 → 要素別質問 → Figma コメントに集約 → 48〜72 時間の期限 → 議事録に決定/保留/宿題。スコープクリープ防止は「Won't 一覧・修正回数（WF 2 回・ベース 2 回・展開 1 回）・前工程戻り別見積・変更要求フォーム」の 4 点セットを価格表と同時に提示する。

### 評価は認知的ウォークスルー・ヒューリスティック・5 人テストと自動ゲートを時期で使い分ける

NN/g は 5 人以内の小規模テストを予算が許す限り繰り返すことを最善とし（[NN/g: 5 Users](https://www.nngroup.com/videos/usability-testing-w-5-users-design-process/)）、ヒューリスティック評価は 3〜5 人が独立に評価（[NN/g: Heuristic Evaluation](https://www.nngroup.com/articles/how-to-conduct-a-heuristic-evaluation/)）、認知的ウォークスルーは各ステップで「正しい効果を得ようとするか／正しい操作に気づくか／操作と効果を結びつけられるか／進捗が分かるか」の 4 問を問う（[NN/g: Cognitive Walkthroughs](https://www.nngroup.com/videos/cognitive-walkthroughs/)）。計画は、WF 完成時に認知的ウォークスルー（タスク: 新規客が「明日 20 時にカット」を英語で予約する／オーナーが枠をブロックする）、ベースデザイン時に 5 秒テスト（知人 5 名）、全画面カンプ時にヒューリスティック評価（日を置いて 2 回＋外部 1〜2 名）、実装中は Lighthouse CI と axe を毎 PR、公開前に実客 1〜2 名＋知人の思考発話テスト（実機スマホ、予約〜キャンセル、各 20〜30 分）。ソロで 3〜5 人の独立評価を満たせない場合はその限界を報告書に明記する。

### 見積は内訳標準＋バッファ可視化、議事録と変更要求は定型にする

日本の制作見積は「ディレクション費／デザイン費（TOP・下層単価）／コーディング費／レスポンシブ対応費／開発費」が標準で（[xserver.ne.jp](https://www.xserver.ne.jp/bizhp/web-site-production-estimate/)）、フリーランス直請けは 10〜50 万円帯が相場とされる（[atsoho.com](https://atsoho.com/blog/web-production-cost)）。WBS は成果物 → 3〜6 フェーズ → 作業に分解してからガントに落とす（[curythm.com](https://curythm.com/blog/wbs-howto/)）。価格表は「基本パッケージ（Must 一式）／オプション（LINE 通知、Google カレンダー同期、写真撮影、文章作成）／次フェーズ概算（チャット・カルテ）／月額保守（ホスティング実費、監視、軽微修正 n 時間/月、規約改訂）／条件（修正回数・検収 14 日・支払条件）」の構成にし、概算工数は「画面一覧×画面種別単価＋Server Action/Route 本数×単価＋横断作業（認証・通知・PWA・テスト・公開・文書）＋ディレクション 15〜25%＋バッファ 20〜30%（使わなければ請求しない）」として可視化する。バッファ率は PMI Lexicon v5.0（2026-01）が contingency reserve（既知リスク向け）と management reserve（未知向け）を定義するのみで固定の割合を定めていないため、「予備 20%（既知リスク分は項目ごとに明記）、未使用分は請求しない」を本案件の運用ルールとして示す。月額保守の参考相場は Web幹事「月額 5,000〜2 万円が約 6 割、平均 4.1 万円・中央値 1.1 万円」、Fyve「5,000 円前後＝ドメイン・サーバ・SSL の維持、1〜2 万円＝不具合修正・バックアップ・軽微修正枠」（[web-kanji.com](https://web-kanji.com/posts/hp-runningcost)、[fyve.co.jp](https://fyve.co.jp/web/blog/homepage-maintenance-cost-guide)）で、含む作業・含まない作業を Fyve の例のように明示する。議事録は「基本情報／議題別の議論と結論／決定事項（主語・対象・数量を省略しない）／確認・保留／宿題（担当・期限）／次回」、送付後 3 営業日で確定扱い（[subanana.com](https://subanana.com/ja/blog/議事録-作り方-テンプレート)）。変更要求フォームは CR 番号・依頼内容・影響範囲・追加工数・納期影響・対応区分（無償/有償/次フェーズ）・承認者。

### 公開は staging ブランチ方式、ロールバックは Pro なら本番履歴の任意デプロイへ戻せる

Vercel のステージングは「カスタム環境（Pro/Enterprise）」「ステージド本番デプロイ（全プラン、ただし本番環境変数を使うためテストが本番 DB に到達するリスク）」「staging ブランチ＋固定ドメイン（全プラン）」の 3 方式があり（[Vercel KB: staging](https://vercel.com/kb/guide/set-up-a-staging-environment-on-vercel)）、Instant Rollback は再ビルドなしで本番ドメインを戻せる。**Pro/Enterprise は本番にエイリアスされた全デプロイへ戻せ、Hobby は直前の本番デプロイのみ**、ロールバック後は自動本番割当がオフになる（[Vercel: Instant Rollback](https://vercel.com/docs/deployments/instant-rollback)）。Deployment Protection は Vercel Authentication と Standard Protection が全プラン（Password Protection は Pro で $20/月/プロジェクト）、**Protection Bypass for Automation も全プラン**で、`VERCEL_AUTOMATION_BYPASS_SECRET` を `x-vercel-protection-bypass` ヘッダに載せれば Playwright E2E を保護された Preview/staging に対して回せる（[Protection Bypass for Automation](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation)）。**採用案**: `main` → 本番、`staging` → 固定ドメイン（Vercel Authentication で保護、Neon の Preview ブランチで DB 分離）、PR ごとのプレビュー、E2E はバイパスヘッダで Preview に対して実行。公開手順書は「0 前提（検収合格・DNS 権限）→ 1 公開前チェック（OGP 1200×630、favicon、404、HTTPS/mixed content、フォーム実送信、title/description、サイトマップ、GA4 または Vercel Analytics、LocalBusiness 構造化データ、実機 iOS/Android、Lighthouse/axe、ポリシーリンク）→ 2 本番環境変数 → 3 データ投入（メニュー・営業時間・休業日）→ 4 staging 最終受入 → main マージ → 5 公開直後テスト（予約 1 件 → 通知 → 管理 PWA で確認 → キャンセル）→ 6 Search Console・Google ビジネスプロフィールの予約 URL 更新 → 7 ロールバック手順 → 8 公開報告」。公開直後の典型的失敗は「フォーム送信でエラー」「SNS シェアで画像が出ない」「favicon が空」である（[library.libecity.com](https://library.libecity.com/articles/01KQDKJQJMWPV1CB5SV6SZN7JT)）。運用マニュアルはオーナー向けに「日次／随時（手動予約・ブロック・休業設定）／月次（バックアップ確認）／困ったとき／アカウント一覧／費用一覧／やってはいけない操作」をスクリーンショット付き日英併記で用意し、レクチャーと引継ぎを契約に明記する（納品＝公開と考えた制作者が公開前レクチャーを求められた事例、[crowdworks.jp](https://crowdworks.jp/consultation/threads/17708)）。

## 予防中心のキャンセル規定と予約状態遷移で現場を回す

美容サロンのキャンセルポリシー相場は「当日 50%・無断 100%」が標準的で（[tol-app.jp](https://tol-app.jp/columns/915)、[stores.fun](https://stores.fun/magazine/articles/beauty-salon-cancellation-fee)）、段階式は「3 日前〜前日 30%／当日 50%／無断 100%」（[kalonade](https://service.kalonade.com/blog/salon-last-minute-cancellation-policy-template)）、遅刻は「連絡なく 15 分以上で無断キャンセル扱いとすることがある」が例文に含まれる（[tol-app.jp](https://tol-app.jp/columns/915)）。ただし消費者契約法 9 条 1 項 1 号により「当該消費者契約と同種の消費者契約の解除に伴い当該事業者に生ずべき平均的な損害の額」を超える部分は無効で、消費者庁の逐条解説はこれを「同一事業者が締結する多数の同種契約事案について類型的に考察した場合に算定される平均的な損害の額」であり**「当該業種における業界の水準を指すものではない」**と明記する（[e-Gov 消費者契約法](https://laws.e-gov.go.jp/law/412AC0000000061)、[消費者庁 逐条解説 第 9 条](https://www.caa.go.jp/policies/policy/consumer_system/consumer_contract_act/annotations/assets/consumer_system_cms203_230915_16.pdf)）。同条 2 項は消費者から説明を求められたとき算定根拠の概要を説明する努力義務を事業者に課すため、「当日 50%／無断 100%」を掲げるなら自店の損害（当該枠の粗利、材料費控除、当日枠の再販率）で説明できる算定根拠メモが必要になる。サロン公式サイト・LINE 公式の実例は「前日 30%／当日 50%／無断 100%、次回来店時に合算請求、15 分以上の遅刻はキャンセル扱いの場合あり」（refu）、「当日 100%／前日 15 時以降 50%」（Early Arrow）、「2 回以上続いた場合に当日 100%／前日 50%」（eNe）で、時刻で切る・回数条件付きで適用する型が実在する。予約画面での同意取得が有効とされ（[jicoo.com](https://www.jicoo.com/magazine/blog/reservation-no-show-cancellation-policy-template)、[financial-field.com](https://financial-field.com/living/entry-349935)）、予約成立時点で契約が成立し無断キャンセルは債務不履行と判断されうる（[squareup.com](https://squareup.com/jp/ja/townsquare/how-to-deal-with-no-shows)）。決済なし・少額の本件では請求コストが見合わないため、**採用案は「請求より予防」**: (1) 予約時にポリシー同意チェック（文言バージョン保存）、(2) 完了画面と ICS の `VALARM` でリマインドを代替（顧客向け自動送信は Phase 1 にない）、(3) `customers.no_show_count`/`late_cancel_count` を記録し 2 回目以降は `booking_restriction = 'phone_only'`、(4) キャンセル料は「当日キャンセル・無断キャンセルが続いた場合、次回以降お電話のみの受付とさせていただくことがあります」程度の裁量条項で 100% 固定を避ける、(5) 遅刻は連絡なし 15 分で施術短縮、30 分で枠解放。リマインドの時刻は業界例の「2 日前 20 時＋前日 10 時」（[aurant-technologies.com](https://aurant-technologies.com/blog/line-official-account-for-beauty-salon/)）を将来の LINE/メール導入時の既定にし、「リマインド」という語自体を避けてあいさつから始める（[squareup.com](https://squareup.com/jp/ja/townsquare/what-is-a-reminder-email)）。

手動予約（電話・店頭・Instagram DM）は管理 PWA の `source` 付きクイック作成フォームで受け、電話番号なしでも作成可能（`phone_unverified`）、**「DM 予約を受けたら必ずシステムに入力してから DM に返信し、確認用 URL を貼る」**を運用ルールにする。これが DM 見落とし・二重予約の直接的な解決策になる。時間ブロックは `blocks(kind: break|closed|private|holiday)` を予約と同じ区間演算で扱い、繰り返しは `weekly_rules`＋`date_overrides` の 2 層で足りる。バッファは `menus.buffer_after_min`（既定 10 分）を所要時間に加算して占有判定し（[support.pabau.com](https://support.pabau.com/en/pabau2/how-to-set-up-and-use-buffer-time-between-bookings)）、放置時間中に別客を挟む「掛け持ち」は Phase 1 では許さない。祝日は `@holiday-jp/holiday_jp`（MIT、TypeScript、[yarnpkg](https://classic.yarnpkg.com/en/package/@holiday-jp/holiday_jp)）で表示のみ行い、祝日営業が一般的な業態なので自動休業にしない。祝日判定は必ず Asia/Tokyo で日付を切る（[holiday-jp-dayjs README](https://cdn.jsdelivr.net/npm/holiday-jp-dayjs@0.1.2/README.md)）。顧客キーは libphonenumber-js で検証した E.164（`+8190…`、[docsearch libphonenumber-js](https://docsearch.algolia.com/mcp/docs/repo/catamphetamine/libphonenumber-js)）に統一し、`phone_e164` UNIQUE と表示用 `phone_display` の 2 列、名寄せは完全一致サジェスト＋かな正規化（NFKC＋カタカナ→ひらがな）の部分一致、重複は `merged_into_customer_id` でマージする。予約は `customers` 行を必ず作って FK で持つ（電話番号文字列で持たない）ことが、チャット・カルテへの拡張で最重要になる。業務 KPI（週次予約数・再来率・無断キャンセル率 `no_show / (completed + no_show + cancelled_late)`・メニュー構成・空き枠率・経路別）は自前 DB の SQL で出し、Web 解析は Vercel Web Analytics（Hobby 月 5 万イベント、Pro ではカスタムイベントも使える、[vercel.com/docs/analytics](https://vercel.com/docs/analytics/limits-and-pricing)）で足り、予約ファネルは各ステップを別 URL にしてページ遷移で代替する。

## LINE 主軸のチャットと要配慮情報を分離したカルテが将来フェーズを接続する

顧客チャット（Phase 2）は、LINE 公式アカウントを主窓口にするのが現実的である。LINE Messaging API はコミュニケーションプラン 0 円・月 200 通、**応答（Reply API）は通数にカウントされない**ため顧客起点の会話に返す限り無料で、プッシュ・マルチキャスト等のみ課金対象になる（[developers.line.biz 料金](https://developers.line.biz/ja/docs/messaging-api/pricing/)、[通数カウント方法 2026-05-28](https://developers.line.biz/ja/tips/2026/05/28/how-to-count-messages/)）。ただしこちら起点の確認・リマインドは通数を消費し、1 予約あたり確認 1＋リマインド 2 = 3 通なら月約 65 予約分で枠が尽きるため、月 100〜150 件ならライトプラン 5,000 円かリマインド 1 通への絞り込みが必要になる。Instagram Messaging API は自アカウントのみなら Standard Access でアプリ審査不要だが（[developers.facebook.com](https://developers.facebook.com/docs/instagram-platform/overview)）、顧客の最終メッセージから 24 時間の返信ウィンドウ（Human Agent タグで 7 日）があり（[inro.social](https://www.inro.social/glossary/24-hour-messaging-window)）、「受信箱への取り込み＋予約リンクの定型返信」に限定する。自前チャットは予約ページ内の軽いやり取り用で、認証はキャンセルリンクと同じトークン、基盤は Supabase Realtime 無料枠（200 接続・月 200 万メッセージ）で足り、Ably Free（200 接続・600 万 msg/月）や Stream（Build 1,000 MAU、次が $499/月）を選ぶ理由は薄い（[Supabase Realtime Limits](https://supabase.com/docs/guides/realtime/limits)、[ably.com](https://ably.com/compare/ably-vs-pusher/pricing)、[getstream.io](https://getstream.io/pricing)）。Neon を Phase 1 で選んだ場合、ここが Supabase へ移る（または Route Handler の SSE を足す）判断点になる。`conversations(customer_id, channel, external_thread_id, owner_unread_count)` と `messages(conversation_id, booking_id, direction, body, attachments, owner_read_at)` は顧客単位をスレッドの正とし、`customers.line_user_id`/`instagram_user_id` は Phase 1 から NULL 列で用意する。

電子カルテ（Phase 3）は国内製品（美歴、LiME、顧客カルテ+POS、Salona）に共通する「基本情報／来店履歴／施術内容／使用薬剤／写真／次回提案／同意書」を項目自由設定で持つのが標準で（[meetsmore.com](https://meetsmore.com/product-services/electronic-karte/media/167720)、[mwm.ai](https://mwm.ai/apps/pos/843977256)、[itreview.jp](https://www.itreview.jp/products/salona/profile)、[it-trend.jp](https://it-trend.jp/reservation/23136)）、LiME は無料プランでカルテ 1 人 5 枚までという制限がある（[saas.imitsu.jp](https://saas.imitsu.jp/cate-crm/service/4634/price)）。設計は `karte_entries(customer_id, booking_id, visited_at, treatments jsonb, chemicals jsonb[{name, brand, level, ratio, ox, grams, process_min, heat}], next_visit_weeks, next_proposal, private_note)`、`karte_photos(kind: before|after|detail, storage_key, sha256)`、そして**要配慮情報になりうる「かぶれ・しみた経験、パッチテスト、妊娠中、皮膚疾患」は `customer_health_notes` に分離し `consent_id` を必須**にする。写真はクライアントで `browser-image-compression`（長辺 1600px、`preserveExif: false`）→ Canvas 再エンコードで EXIF を除去し（[orthogonal.info](https://orthogonal.info/how-browser-image-compression-actually-works-canvas-api-toblob-and-why-your-jpegs-shrink/)、[browser-image-compression](https://docsearch.algolia.com/mcp/docs/repo/donaldcwl/browser-image-compression)）、orientation 補正を忘れない。ストレージは Cloudflare R2（10 GB-月無料、エグレス無料、[developers.cloudflare.com](https://developers.cloudflare.com/r2/pricing)）が最有力で、Supabase Storage Free は 1 GB・画像変換は無料枠外（[supabase.com](https://supabase.com/docs/guides/storage/pricing)）、Vercel Blob Hobby は 1 GB（[vercel.com](https://vercel.com/docs/vercel-blob/usage-and-pricing)）。1 来店 2〜4 枚 × 約 300 KB ≒ 1 MB、月 150 来店で 150 MB/月なら R2 無料枠で約 5 年持つ。写真同意は `photo_consents(scope: karte_only|sns|ads)` で既定 karte_only、SNS 掲載は別チェックと撤回導線（同意書の項目: 撮影日・掲載媒体・期間・利用範囲・撤回方法、[atsoho.com](https://atsoho.com/blog/salon-before-after-photo-shoot-cost)）。放置時間は薬剤行ごとに「塗布開始／放置開始／流し」のワンタップ・タイムスタンプで自動算出し、施術中に片手で押せる大きさにする。オフライン記録は IndexedDB にドラフトを置き復帰時に同期（1 人運用なので最後の保存が勝つ）。美容師法・同施行規則に顧客記録の作成・保存義務はないことを e-Gov 法令 API の全文で確認済み（医師法 24 条の診療録 5 年保存とは異なる）なので、保存期間は Phase 1 の「最終来店から 3 年で匿名化」に合わせる。

## Conclusion

8 領域を突き合わせて見えたのは、この案件の難しさが「機能の多さ」ではなく「制約の少なさ」にあるということだ。決済なし・メールなし・アカウントなし・即時確定という選択は顧客の摩擦を最小化する一方で、二重予約・枠の埋め立てスパム・無断キャンセル・連絡手段の欠如といったリスクをすべてシステム設計と運用ポリシーで引き受けることを意味する。だからこそ DB 排他制約、Turnstile＋レート制限、トークンのハッシュ保存、完了画面の証憑化、`no_show_count` による段階制限、ICS の `VALARM` といった「見えない仕組み」が、ベージュとえんじの見える部分と同じ重みで要件定義書に載る必要がある。

もう一つの含意は、Phase 1 の小さな決定が将来を規定する点である。`customers` を必ず行として作ること、`resource_id` と `source` と `consents` を最初から持つこと、Neon と Supabase の分岐点をチャットの時期に置くこと、ペイロードを Declarative Web Push 形に揃えること。これらはいずれも追加コストがほぼゼロでありながら、2 席化・LINE 連携・カルテ・iOS の宣言的通知への移行を DDL 変更なしに可能にする。次工程では、本レポートの 3 つの判断表（デザイン・技術・運用）をそのまま要件定義書の MoSCoW 表と ADR の初期 7 本に転記し、未確認事項を第 2 回会議前に潰すのが最短経路である。
